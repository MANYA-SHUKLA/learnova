# ADR 0003: MongoDB + Redis

- **Status:** Accepted
- **Date:** 2026-08-06
- **Deciders:** Platform team

## Context

Domain data is document-shaped (courses, exams, submissions, IDE sessions) with evolving schemas. We also need caching, rate limits, sessions, and job queues.

## Decision

### MongoDB (Mongoose)

**Why MongoDB?**

- Flexible documents fit LMS/ERP/exam payloads that grow over time
- Horizontal scale story for multi-tenant SaaS
- Strong Node.js ecosystem (Mongoose ODM)

Models are intentionally **not** created in the foundation phase — connection layer only.

### Redis (ioredis + BullMQ)

**Why Redis?**

| Use | Reason |
| --- | --- |
| Sessions / revocation | Fast key lookup + TTL |
| Rate limiting | Atomic counters (`rate-limit-redis`) |
| Cache | Hot reads (catalogs, permissions) |
| Queues | BullMQ for email, grading, analytics, audit |

## Consequences

- Two operational stores to back up and monitor
- Must define key namespaces (`REDIS_KEYS`) to avoid collisions
- Eventual consistency between Mongo writes and Redis cache is app-owned

## Alternatives considered

| Option | Why not |
| --- | --- |
| PostgreSQL only | Rigid early schema; JSONB still less natural for nested course trees |
| Mongo only (no Redis) | Poor fit for queues, rate limits, ephemeral sessions |
| RabbitMQ / SQS for jobs | Extra infra; BullMQ on Redis is enough for v1 |
